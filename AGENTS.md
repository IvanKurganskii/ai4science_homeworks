# AGENTS.md — Очистка и моделирование спектров ВР ЭПР Д-А диад с Периленбисимидом

Проект по разработке агента для параметризации спектров время-разрешённой спектроскопии электронного парамагнитного резонанса с учётом отработанного пайплайна их анализа

## 0. Цель и образ результата

Обработка спектров ЭПР-спектроскопии с временным разрешением (ВР ЭПР)

В конце работы в проекте существуют:
- `/results/spectra/slices` — каталог со срезами 2-х мерных спектров по оси магнитного поля в выбранные моменты времени 
- `/results/spectra/processed` — каталог со спектрами, очищенными от сигналов подложки, выбросов; к спектрам применены фильтры, которые не изменяют интерпретируемость
- `/src/ai4science_cleaning/` — скрипты, которые создал агент для обработки спектров в процессе работы
- `/results/tables/1d-fit_results.csv` — файл с результатами моделирования срезов ВРЭПР-спектров (параметры спиновых гамильтонианов и населённость в моменте среза)
- `/results/tables/2d-fit_results.csv` -- файл с результатами моделирования кинетических параметров спектров. Параметры спин-гамильтонианов берутся из 1d-симуляций

Проект — хранилище Obsidian: каждый файл проекта — узел графа, ссылки `[[…]]` —
рёбра. Пользователь ставит задачи словами в сессии. Твоя работа:

1. записать задачу пользователя заметкой в `tasks/` и разделить её на подзадачи, если необходимо;
2. выполнять подзадачи по очереди, вести их статусы и по каждой сообщать итог, изменять их статусы;
3. по ходу работы достраивать граф проекта по онтологии `ontology.yaml`.

Новая сессия начинается с чтения `tasks/`, определять по статусам, что сделано, что в работе и что ждёт пользователя.

После каждого сообщения пользователя в проекте существуют:
- заметки задач и подзадач с актуальными статусами и итогами;
- результаты выполненных подзадач — то, что требует их «Готово, когда»;
- заметки обо всех объектах работы в `notes/`, связанные между собой и с файлами;
- заметки классов онтологии в `ontology/`; настройки хранилища в `.obsidian/`.

### 2.2. Онтология в графе

`ontology.yaml` — схема: классы, отношения, правила. Прочитай её первой. Для каждого
класса из `ontology.yaml` должна существовать заметка `ontology/<Класс>.md`:

```
---
kind: класс
---
# <Класс>

<определение из ontology.yaml>

Отношения от этого класса: <отношения, у которых класс в domain>.
Атрибуты: <атрибуты, у которых класс в domain, с допустимыми значениями>.

## Связи
- подклассОт: [[<надкласс>]]
```

У верхних классов (`parent: null`) раздел «Связи» пустой. Если заметок классов нет или
`ontology.yaml` изменился — создай или обнови их; удобно сделать это одним скриптом на
Python, который читает `ontology.yaml`.

### 2.3. Заметки об объектах

Каждый объект работы — заметка `notes/<название>.md`:

```
---
type: <Класс>
---
# <название>

<2–4 строки: что это, откуда взято, числа с единицами>

## Связи
- тип: [[<Класс>]]
- <отношение>: [[<название другой заметки>]]
- хранитсяВ: [[<путь к файлу от корня проекта>]]
```

Правила:
- Название называет экземпляр: «Fit\_<Experiment\_name>_<integration\_window>\_YEAR-MONTH-DAY\_v#» для 1d фита, «Fit\_<Experiment\_name\_YEAR-MONTH-DAY\_v#» для 2d-fit; «spec\_<Experiment\_name>_<integration\_window>\_YEAR-MONTH-DAY\_v#» для среза по магнитному полю; «kin\_<Experiment\_name>_<integration\_window_in_G>\_YEAR-MONTH-DAY\_v#» для кинетик. Не использовать названия классов для названия заметок.
- В названии нет символов `/ \ : # | [ ]`: пиши «кДж на моль», «ln k от 1 на T».
  Символ `/` создаёт вложенную папку, и ссылки на заметку ломаются.
- Строка `- тип: [[<Класс>]]` обязательна: она связывает объект с его классом в графе.
- Остальные связи — только отношения из `ontology.yaml`, от области определения к
  области значений. Связь записывается в заметке, от которой она идёт.
- Файлы проекта — данные, код, результаты, отчёты, тексты источников в `library/` —  отдельные заметки не получают: на них ссылаются по пути от корня, например
  `[[data/raw/rates.csv]]`, `[[src/fit.py]]`, `[[library/arrhenius_1889.md]]`.
- Источник — заметка `notes/<автор год>.md` с типом `Источник` и связью
  `хранитсяВ: [[library/…]]`. Связи `основанаНа` и `ссылаетсяНа` ведут к заметке
  источника; к файлу в `library/` ведёт только `хранитсяВ`.
- Отчёт пишется, только если пользователь просил отчёт. Отчёт — сам файл
  `reports/<название>.md`: в начале `type: Отчёт`, в конце раздел «Связи», как у
  заметок объектов. В тексте отчёта утверждение, взятое из источника, сопровождается
  ссылкой на заметку источника: «… [[Laidler 1984]] ».
- Ссылки `[[…]]` в тексте заметок не берутся в обратные кавычки: внутри кода Obsidian
  их не показывает.
- Каждый ВР ЭПР эксперимент — отдельная заметка `ВРЭПРэксперимент`, связанная с общим набором  отношением `входитВ` и с файлом отношением `хранитсяВ`. Эксперимент связан отношением  `использует` с каждой серией, взятой в расчёт.
- Объект, для которого в онтологии нет класса, — новый тип и строка «Новый тип:
  <почему>». `ontology.yaml` не меняй: решение о новом классе принимает пользователь.
- Заметку создавай в момент, когда объект появился в работе: набор данных — при
  чтении, метод — при выборе, результат — после расчёта, проверку — после проверки.
- Заметка, которая закрывает подзадачу, ссылается на неё: эксперимент и проверка —
  `решает`, отчёт — `выполняет`.

### 2.4. Задачи

Сообщение пользователя, которое требует работы с файлами проекта, — новая задача
верхнего уровня, даже если она продолжает прежнюю. Вопрос, на который достаточно
ответить словами, задачей не становится.

Заметка задачи — `tasks/<название>.md`, название — действие: «Проверить закон
Аррениуса», «Рассчитать E_a по трём сериям». Названия заметок во всём проекте
различны: задача «Рассчитать E_a…», эксперимент «Расчёт E_a…».

```
---
type: Задача
status: открыта
---
# <название>

Запрос пользователя: «<его слова дословно>»   (только у задачи верхнего уровня)

Готово, когда: <проверяемое условие: файл, число, команда и её результат>
Не входит: <что делать не нужно>

## Связи
- тип: [[Задача]]
- подзадачаОт: [[<родительская задача>]]   (только у подзадачи)
```

Подзадачи:
- Если необходимо, раздели задачу на 2–5 подзадач: каждая заканчивается объектом, который её закрывает
  (эксперимент, проверка или отчёт). Порядок выполнения — раздел «План» в заметке
  родительской задачи: названия подзадач по строке, без ссылок.
- Запиши задачу и все подзадачи со статусом «открыта» до любых расчётов и покажи план
  пользователю: по строке на подзадачу. Чисел, которых ещё нет, в заметках задач не пиши.

Статусы (поле `status`):

| статус | кто ставит | когда |
|---|---|---|
| открыта | агент | задача записана |
| в работе | агент | начал выполнять |
| выполнена | агент | условие «Готово, когда» проверено командой; раздел «Итог» записан |
| заблокирована | агент | условие недостижимо: причина и вопрос пользователю в разделе «Итог» |
| принята | агент | существует подтверждение выполнения |

- Статус меняется в момент события, по одной подзадаче: «в работе» — до первой команды
  подзадачи; «выполнена» и итог — сразу после проверки её условия, до начала следующей.
  По статусам в Obsidian пользователь видит ход работы.
- При статусе «выполнена» — раздел `## Итог` перед «Связями»: что сделано, какие файлы и
  заметки появились, чем проверено (команда и результат), 2–5 строк. Итог выводи и
  пользователю в сессии.
- Родительская задача выполнена, когда выполнены все её подзадачи; её итог — сводка по
  подзадачам.
- «Принята» ставится только после слов пользователя «принимаю» (или равных по смыслу) и
  распространяется на подзадачи. В итог допиши строку «Принято пользователем: «<его
  слова>»». Просьба переделать возвращает задачу в статус «в работе».
- Принятая задача закрыта: новые заметки не ссылаются на неё связями `решает` и
  `выполняет`. Новая работа — новая задача; связь с прежней работой идёт через объекты:
  отчёт `описывает` эксперимент и результат.

`/data/mars_examples` — примеры использования библиотеки mars-epr
`/src/mars_cleaning` — полезные скрипты для обработки спеткров, использующие функционал библиотеки mars-epr

Агент не знает сам:

Запрос. Каждое обращение к внешнему графу, результат которого попадает в проект, —
заметка `notes/Запрос <дата> <кратко>.md`:

```
---
type: ЗапросКГрафу
source: OpenAlex
retrieved: <дата из поля provenance>

# Запрос <дата> <кратко>

Инструмент и аргументы: <имя инструмента и значения аргументов; для SPARQL — текст запроса>
Найдено: <число из ответа>; отобрано в проект: <число> — <по какому условию>

## Связи
- тип: [[ЗапросКГрафу]]
- решает: [[<подзадача>]]
```

Источник. Найденная работа — заметка `notes/<Фамилия год>.md`; при совпадении названий —
`<Фамилия год б>`:

```
---
type: Источник
openalex_id: <W… из ответа>
doi: <из ответа; нет — поле не пишется>
year: <год>
cited_by: <число цитирований из ответа>
oa_status: <значение из ответа>
---
# <Фамилия год>

[источник] <авторы, название, журнал, том, выпуск, страницы, год — как в ответе инструмента>
[источник] Аннотация: <1–3 предложения из поля abstract; нет поля — «аннотации в OpenAlex нет»>
[порождено] Зачем проекту: <одна строка>

## Связи
- тип: [[Источник]]
- найденЗапросом: [[Запрос <дата> <кратко>]]
- написан: [[<имя автора, как в ответе инструмента>]]
- цитирует: [[<другой источник проекта>]]
- хранитсяВ: [[library/<файл>]]
```

Правила:
- Выходные данные переносятся из ответа инструмента без изменений. Чего в ответе нет, в
  заметке нет. Расхождение ответа с файлом в `library/` записывается строкой
  «Расхождение: …» и сообщается пользователю.
- Пометки в заметках и отчётах: `[источник]` — перенесено из ответа инструмента или из
  файла `library/`; `[порождено]` — написано агентом; `[написано]` — слова пользователя.
- Автор — заметка `notes/<имя автора, как в ответе инструмента>.md` с типом `Автор` и
  полем `openalex_id` автора в начале файла. Заметка создаётся только вместе со связью
  `написан` в заметке источника: для первых трёх авторов работы. Один человек — одна
  заметка.
- Связь `цитирует` — только между источниками, которые есть в проекте, и только если её
  подтверждает `openalex_links` или список литературы в файле `library/`.
- Источник, который уже есть в проекте, не дублируется: в его заметку дописываются поля
  из ответа и связь `найденЗапросом`.
- Если одной работе отвечают несколько записей OpenAlex, запиши идентификаторы всех в
  тексте заметки, в поле `openalex_id` — запись с большим числом цитирований; сообщи
  пользователю.
- Открытая версия: если `oa_url` не пуст, запроси скачивание через загрузчик
  по правилам раздела 3.3. После подтверждения файл сохраняется в `downloads/`;
  свяжи его отношением `хранитсяВ`. Если файл не получен, в заметке источника
  остаётся строка «Открытая версия: <oa_url>».
  Нет открытой версии или файла — задача этим не блокируется, в итоге перечисляются
  работы без локальной копии.
- Сущность Wikidata записывается в заметке объекта, к которому относится: строка
  «[источник] Wikidata: <Q…> — <подпись>; <свойство>: <Q…> — <подпись>» и связь
  `найденЗапросом` не нужна; запрос записывается заметкой `ЗапросКГрафу`, в тексте
  которой перечислены заметки, куда внесены сведения.
- Параметры отбора (годы, тип, сортировка, число записей) берутся из задачи и
  записываются в заметке запроса.

### 3.1. Проверка больших файлов и экономия контекста

Числовые данные проверяй программно, сохраняя контекст компактным.
Чтение статей и текстовой документации описано отдельно в 3.2.

- Перед чтением определяй размер и формат файла.
- Спектры, числовые массивы и большие таблицы проверяй скриптами по всему содержимому.
  В контекст выводи только краткую сводку: размеры данных, результаты проверок,
  количество ошибок и не более пяти примеров.
- Для спектров проверяй наличие ненулевых интенсивностей, NaN и Inf.
  Чтение нескольких первых строк не заменяет проверку всего массива.
- Код и журналы читай через поиск и ограниченные диапазоны.
  Диагностический вывод — не более 100 строк и 6000 символов, включая сообщения об ошибках.
  Ограничивай и строки, и символы: одна строка может содержать большой массив.
- Полные журналы и подробные результаты сохраняй в файл внутри проекта.
  В ответ инструмента включай итог, исходный код завершения и путь к подробностям.
- Если диагностика усечена, уточни поиск или вычисли нужную характеристику скриптом.
  Не загружай числовые данные последовательными фрагментами ради их проверки.
- Артефакты инструментов исследуй через `search_artifact(id, query)`;
  `load_artifact(id, offset, max_chars)` используй только для нужного участка.

### 3.2. Чтение и подготовка статей

- Статьи, рефераты и текстовую документацию можно читать объёмом до 20000 символов
  за вызов. Ограничение диагностики в 100 строк на такое чтение не распространяется.
- Небольшие значения по умолчанию сохраняются: `pdf_read` — 8000 символов и первые
  5 страниц, `web_fetch` — 3000 символов, `load_artifact` — 4000 символов.
  Для статьи явно задавай `max_chars=20000` при извлечении текста и чтении артефакта;
  у `load_artifact` также задавай `max_lines=0`. Его общий ответ вместе с метаданными
  ограничен 20000 символами.
- Перед чтением PDF проверь `pdf_info` и выбери нужные страницы.
  Проверяй диапазон и маркеры усечения: фрагмент не считается всей статьёй.
- Более длинные статьи читай по разделам или страницам. Полное чтение по частям
  допустимо, если задача требует анализа всего источника. Не перечитывай уже
  изученные части без необходимости.
- Эти ограничения относятся к чтению и диагностике. Создаваемую статью записывай
  в файл нужного объёма, при необходимости по разделам.

### 3.3. Скачивание файлов только с разрешением пользователя

- Любой новый файл из сети (PDF, HTML, архив, данные, код) получай только через
  `downloads-mcp__download_file(url, filename, purpose)`. Один вызов — один файл.
- Перед получением файла загрузчик показывает URL, цель и путь и запрашивает
  явное согласие пользователя. Согласие на предыдущий файл, молчание и просьба
  исследовать тему не разрешают новые скачивания. Каждый новый адрес
  перенаправления подтверждается отдельно.
- При отказе или недоступном подтверждении файл не скачивай и не ищи обходной путь.
  Параметра самостоятельного подтверждения у инструмента нет.
- Файлы сохраняются в `downloads/` без перезаписи существующих. Исходные загрузки
  доступны агенту для чтения; рабочие копии и результаты сохраняй в `results/`.
- Поиск записей, связей и аннотаций OpenAlex/Wikidata не требует подтверждения
  скачивания. HTML-страницу или полный текст статьи получай через загрузчик.
- Прямые `web_fetch` и `pdf_download` отключены. Не используй curl, wget,
  Python, установку пакетов, удалённые изображения или новые расширения для обхода.
- Оболочка агента запускает команды и все их дочерние процессы без сети,
  независимо от того, в какой папке лежит скрипт. Обычный терминал пользователя
  вне агента это ограничение не затрагивает.
- Для локальных правок используй защищённую оболочку. Запись разрешена в `src/`,
  `results/`, `tasks/`, `notes/`, `ontology/`, `reports/`, `memory/` и существующие
  `diary.md`, `.obsidian/app.json`, `.obsidian/graph.json`. Управляющие файлы,
  настройки и код обвязки из неё менять нельзя.

7. Не ставить статус «принята» без слов пользователя. `[окно]`

## 5. Протокол работы

1. Прочитать `ontology.yaml`, заметки `tasks/` (статусы) и `diary.md`.
2. Проверить хранилище и заметки классов (2.1, 2.2).
3. Если сообщение принимает результат или просит переделать — сменить статусы (2.4).
4. Если сообщение ставит новую работу — записать новую задачу и подзадачи до любых
   расчётов, показать план. Сообщение может и принять прежнюю работу, и поставить
   новую: тогда сначала шаг 3, затем шаг 4.
5. Подзадачи по очереди: «в работе» → работа и заметки объектов по ходу (2.3) →
   проверка условия «Готово, когда» → «выполнена» и итог. Объём работы задают
   «Готово, когда» и «Не входит»: лишнего не создавай.
6. Когда все подзадачи выполнены или до исчерпания лимитов остаётся <200000 токенов, дописать `diary.md`; ответить пользователю: итоги подзадач, что ждёт его решения.

Для каждой подзадачи по очистке спектра:
Режим — конвейер с рассуждениями:
1. просмотреть скрипты в папке `/src/mars_cleaning` и их документацию
2. получить скриптом список файлов, метаданные и краткую сводку данных из `/data/raw_spectra` по правилам 3.1
3. выбрать методы и инструменты очистки
4. провести очистку спектров от постоянных шумов и явных выбросов
5. провести анализ необходимости и возможности применения фильтров
6. запустить фильтры, если возможно. 
7. сохранить результаты в папке `/results/spectra/processed`
8. найти максимумы по абсолютной интенсивности сигналов. Проинтегрировать их и сохранить в папке `/results/spectra/slices`
9. найти момент времени, когда форма сигнала перестаёт изменяться во времени. Если новая форма отличается от формы в максимуме и от шума, проинтегрировать, добавить результат в папку `/results/spectra/slices` 

Для каждой подзадачи для моделирования спектра:
Режим — конвейер с рассуждениями:
1. просмотреть скрипты в папке `/src/mars_simulation` и их документацию
2. получить скриптом список файлов, метаданные и краткую сводку данных из `/results/spectra/processed` и `/results/spectra/slices` по правилам 3.1
3. начинай моделирование со срезов, используя скрипты из `/src/mars_simulation`
4. если для моделирования не хватает скриптов, можешь написать свои, опираясь на скрипты из папки `/src/mars_simulation`, а также документацию и примеры из папки `/library/mars_documentation`. В том числе можешь использовать подключённые к `mars` оптимизаторы из библиотек `nevegrad` и `optuna` (см документацию и примеры)
5. запусти скрипт, изучи отличие его результата от эксперимента, измени параметры
6. Сами спектры не смотри. Используй скрипты для получения loss-function
7. продолжай, пока не достигнешь хорошего согласия симуляции с экспериментом (точная точка выхода зависит от качества экспериментальных данных)
8. сохранить результаты (параметры спинового гамильтониана и населённости в момент времени, симуляции спектров) в папке `/results/fits/1d`
9. повторить для второго среза, если он есть
10. параметры спинового гамильтониана не меняй
11. если их изменение потребуется, фитируй одновременно все срезы
12. если согласия параметров спиновых гамильтонианов для двух срезов достичь не удаётся, укажи на причину, связанную с описанием данных
13. определив параметры спиновых гамильтонианов, используй их для подбора параметров населённостей и их кинетик для описания 2d-спектров
14. изменяй (варьируй) параметры спинового гамильтониана, **только** если не удаётся достичь хорошего согласия с экспериментом (определи критерий из качества данных) после 100 попыток или 1 часа работы
## 6. Память

- `tasks/` — что поставлено и в каком состоянии; `diary.md` — журнал сессий.
- `diary.md` — дописывается в конце работы над сообщением: дата, сообщение пользователя  кратко, задачи и смены статусов, что появилось в графе, команда проверки и её код.

## 7. Остановка и эскалация

- Бюджет эпизода (ответ на один запрос пользователя): 500000 токенов, 1 час, 40 шагов на сообщение пользователя.
- При исчерпании бюджета: отчёт — что сделано, что нет, где остановились.
- Если проверка подзадачи не проходит дважды подряд по одной причине — статус
  «заблокирована», причина и вопрос пользователю.
- Если проверка не проходит дважды подряд по одной причине — остановись и
  опиши причину.

### 7.1. Автоматический переход на резервную модель
(опция добавлена, так как агент не контролирует лимиты в цикле выполнения подзадачи. Опция позволяет закончить выполнения подзадачи и сохранить контекст для продолжения задач в следующей сессии агента)

- Перед началом новой подзадачи и после завершения текущей проверяй `token_budget()`.
- При автоматическом переходе с Yandex на Ollama из-за исчерпания суточного лимита
  или HTTP 429 сообщи об этом пользователю. Сигнал — служебное уведомление AI4Science
  в запросе модели или сообщение `token_budget()` о резерве из-за лимита Yandex.
- Заверши только уже начатую подзадачу: выполни необходимые проверки, сохрани
  результаты, актуальные статусы и запись в `diary.md`. Не начинай следующую
  подзадачу и не расширяй план.
- Если завершение невозможно в пределах бюджета эпизода, сохрани промежуточный
  результат и укажи оставшуюся работу. Незавершённую подзадачу не помечай выполненной.
- После сохранения состояния кратко сообщи итог, запроси дальнейшие инструкции
  пользователя и закончи ответ. До нового сообщения пользователя работу не продолжай.
  Если работа ещё не начата, сначала запроси указания.
- Восстановление Yandex не отменяет эту остановку. Ручной выбор Ollama или запуск
  с `--provider ollama-cloud` сам по себе её не вызывает. Если после сообщения
  об этом событии пользователь дал новые указания или явно разрешил продолжение на
  Ollama, выполняй их; повтор уведомления с тем же идентификатором события
  не считается новым переходом.
